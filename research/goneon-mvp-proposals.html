What the research changed about the brief

The brief describes goNEON as a utility-network company and gives sewer, power line, and tree examples. Public sources tell a different story, and it works in your favour: an above-ground MVP is closer to their real product than the brief's framing suggests.

The company is goNEON Agentic Systems AG

ETH Zürich spin-off, CEO Raphael Eder, CTO Lukas Ballo. Live site is goneon.city; goneon.io returns 404. Venture Kick funding reported by Tech.eu on 20 July 2026.

Their product is a chat agent over a 3D map

The N! demo at try.goneon.city takes prompts like "Redesign parking spots with 2.5 m width", regenerates geometry, and shows Valid / Invalid / Safety margin / Remaining road width layers with a compare mode. That shape is the template to copy.

Every public use case is above ground

Lane-level network scenarios, parking and curb compliance, cycling corridors scored on directness, gradient, turning angles and traffic exposure, loading-zone inventories, sight-triangle permit checks. No sewer, water, or district heating anywhere.

The CTO's own toolkit is open source

SNMan (MIT) reallocates road space on OSM streets under design rules while keeping motorised traffic connected. Whole-city runs take hours, so it is a reference and a "next step" engine, not a drop-in.

Two more findings shape every proposal below. First, the reference architecture that matters is a small set of deterministic, well-typed tools with domain rules injected, not a free-form code sandbox. GISclaw's authors found agent success bounded more by tool design than by model reasoning, and GISAgentBench reports the best agent completing only about a third of realistic GIS tasks. Second, your existing scaffold in this repo already speaks the right dialect: FastAPI, Shapely in LV95 metres, swisstopo heights, canton Zürich WFS, the city tree cadastre, and an A* least-cost alignment router. Zürich is also goNEON's home city and the setting of their demo.

Ranking

Demo impact is how strongly a two-minute video lands with Lukas and Raphael. Build risk is the chance that a single autonomous run does not reach an end-to-end usable state by morning. Rules and data marked verified were fetched live on 7 September 2026.

Recommendation: build Clearance, ship Rulebook as its ecosystem hook, keep Canopy as the fallback

Clearance reuses the alignment router and Swiss data layer you already wrote, so the run starts from working geometry rather than a blank repo. It is the only proposal with a natural 3D "wow" moment: extruded buildings turning red inside a protective strip, then the line bending clear. Rulebook turns its clearance table into editable, attributed rule packs, which is the exact vocabulary goNEON uses for its own product and the thing a third party would extend.

Set one checkpoint. If by roughly hour five the corridor check is not drawing conflicts on real OSM lines, switch the same agent loop and UI to Canopy. The tools, rule schema, and export format are shared, so the switch costs the engine only.

The six proposals

Rank 1

Clearance

Drop a 110 kV line on the map, see every building and tree inside its protective strip, then let the agent bend it clear.

60-second demo

Pick a real overhead line at the edge of Zürich. Type "Show the protective strip for this line as an E.DIS 110 kV standard design". A 46 m corridor sweeps along the route; buildings inside rise in red with their height. Type "Realign to clear the school, at most two new angle towers". The router redraws the line, the compare panel shows +11 % length and 0 conflicts. Export GeoJSON.

Agent tools
  • fetch_lines(bbox) → OSM power=line and minor_line with voltage and tower nodes
  • corridor(line_id, ruleset) → protective strip polygon
  • find_conflicts(corridor) → buildings, trees, masts with reasons
  • realign(line_id, constraints) → new alignment via least-cost A*
  • score(alignments) → length, angle towers, conflicts
  • fly_to, toggle_layer, compare
Data

Verified: OSM separates overhead from underground cleanly. power=line and power=minor_line both imply overhead; underground is power=cable. Only about 0.1 % of line objects carry a location tag, so a query excluding location=underground returns more than 99.8 % overhead lines. Overture buildings carry optional height, num_floors, min_height and roof_height, and these survive the DuckDB to tippecanoe PMTiles pipeline for MapLibre fill-extrusion.

From your scaffold, not re-verified: canton Zürich cadastral land cover and objects, swisstopo heights.

Rules

Verified, E.DIS Netz guideline (January 2022, based on DIN EN 50341): 110 kV standard protective strip of 46 m, 23 m each side of the axis, kept free of buildings; woody plants inside limited to 3.0 m final height; trees outside placed so they cannot fall into the line; 15 m planting-free radius around each mast foundation.

These are one operator's standard-design values, so encode them as an editable rule pack with source attribution and an operator selector, never as constants.

Engine
Buffer and intersection in Shapely on LV95 metres. Realignment uses the A* raster router already in server/engines/route.py, with the corridor width as the impassable buffer around buildings.
Wow visual
MapLibre 3D extrusions from a static PMTiles file, corridor drawn as an animated sweep, conflict counter ticking down as the realignment is drawn live, reasoning trace streaming beside the map.
Ecosystem hook
Rule packs as JSON per grid operator, each field carrying its source and page. An MCP server exposing the same six tools so any agent client can plan against the engine. GeoJSON and KML export.
One-night plan
1.0 hOverpass fetch and tower nodes, PMTiles buildings for one bbox2.0 hCorridor, conflict, and score tools with tests on a fixture line1.5 hWire realign to the existing A* router2.0 hMapLibre UI: layers, compare panel, streaming trace1.5 hTool-calling loop, manual panel without API key1.0 hDeploy, instructions page, MCP server stub

About nine hours of agent run time. Rulebook adds two.

Cut first
Realignment. A check that only flags conflicts and lets the planner drag the line is still end-to-end usable. Then cut 3D in favour of 2D footprints.
Risk
City-centre lines are underground cables, so demo on a suburban or rural bbox. Overture heights are sparse in many regions; fall back to num_floors × 3 m or a default.
Scores well because
It reproduces the N! pattern of parameter, constraint check, valid and invalid layers, compare. It is explainable in three sentences of geometry. Rule packs show how another operator's engineer extends it.
Rank 2

Canopy

Draw a street, get every legal tree position and the shade those trees will cast in thirty years.

60-second demo

Type "Plant as many street trees as possible on Langstrasse, Berlin standard clearances, 8 m spacing". The agent loads existing trees, carriageway edges, cycle paths and building fronts, proposes positions, and the crowns grow to mature diameter. Invalid positions show red with the rule that killed them. "Compare 8 m and 10 m spacing" shows canopy cover for each. Export GeoJSON.

Agent tools
  • query_trees(bbox) → live cadastre features
  • street_edges(segment) → carriageway, cycle path, building front lines
  • candidate_sites(segment, spacing)
  • check_clearances(sites, rules) → valid / invalid with reason
  • canopy_gain(sites, species, years)
  • export_geojson
Data

Verified live: Berlin's tree cadastre WFS 2.0.0 at gdi.berlin.de serves 434,765 street trees as GeoJSON in EPSG:4326 with CORS enabled, each with species, genus, planting year, age, crown diameter, trunk circumference and height. About a fifth of records have missing crown diameter, so impute from species and age. Filter by bbox, never pull the full set.

From your scaffold, not re-verified: Zürich Baumkataster WFS, so the same tool can run in goNEON's home city through a city adapter.

Rules

Verified, Berlin street-tree planting standard (September 2024, section 5.2): at least 0.5 m from carriageway edge to trunk, mandatory; at least 0.25 m from trunk to cycle path, recommended; at least 1.5 m from mature crown edge to multi-storey buildings, recommended. Render mandatory and recommended differently.

Engine
Pure 2D buffers and intersections in Shapely. Mature crown diameter from a small species table. Shade as a shadow polygon offset by tree height for one sun position, if time allows.
Wow visual
Crowns animating from sapling to mature size, canopy percentage rising in the corner, a July afternoon shadow layer, side-by-side spacing scenarios.
Ecosystem hook
City adapters: one small class per WFS turns Berlin into Zürich or Munich. Species table as a plugin file. Same rule-pack format as Clearance. MCP server over the tools.
One-night plan
1.0 hWFS adapter with bbox paging, Overture footprints, OSM ways2.0 hCandidate sites, clearance check, canopy gain, tests2.0 hMap UI with growth animation and compare1.5 hAgent loop and manual panel1.0 hDeploy and instructions

About eight hours. The safest build on the list.

Cut first
Shade. Then species imputation, using an 8 m default crown.
Risk
Low. The only live dependency is a public WFS that answered every probe on 7 September.
Scores well because
Works end to end with the least engine code. A planner understands it in one sentence. The rule numbers are real and cited, which answers "explain what it does" before the question is asked.
Rank 3

Rulebook

Feed the agent a planning standard as a PDF; it writes the rule pack and runs it on the map in the same minute.

60-second demo

Drop the Berlin tree standard or the E.DIS guideline onto the page. The agent extracts each distance with its page reference into a rule pack shown beside the PDF page, numbers highlighted. Move the 0.5 m slider to 0.75 m and the map re-validates instantly. Load a second pack and diff them.

Agent tools
  • extract_rules(pdf) → schema-constrained LLM call
  • validate_rules(pack) → schema and unit checks
  • apply_rules(features, pack) → valid / invalid with rule ids
  • diff_rules(a, b)
  • explain_rule(id) → quote and page
Data
Whatever engine it sits on. The two verified PDFs above are the demo inputs and ship pre-extracted as fallbacks.
Rules
The rule schema is the product: subject, reference feature, minimum distance, mode (must or should), source document and page, operator or city scope.
Engine
One generic buffer-check runner over GeoJSON that both Clearance and Canopy already need. Rulebook is that runner with a schema and a PDF front door.
Wow visual
Split screen: the PDF page with highlighted numbers on the left, the map turning valid and invalid on the right as each rule lands.
Ecosystem hook
This is the platform story in one artifact. Each hackathon team submits a rule pack; a registry lists them with sources; the engine runs any of them. goNEON's own site describes its product as machine-readable design rules over a constraint-aware spatial model, so this speaks their language exactly.
One-night plan
1.0 hRule schema, validator, two hand-checked packs1.0 hPDF extraction call with page citations1.0 hSplit-screen UI and diff view

Three hours on top of Clearance or Canopy. Not worth building alone.

Cut first
Live extraction. Keep the editable packs and the diff; show extraction only on the two known PDFs.
Risk
PDF extraction is the flaky step. A refuted claim in this research, voltage-tiered 10, 20, 30 m distances attributed to DIN EN 50341, is exactly the kind of number an extractor can hallucinate, so every extracted value must show its quote.
Scores well because
It is the clearest answer to "show how other people could build on it with you".
Rank 4

Corridor

Three bike corridors between two points, scored the way goNEON scores them: directness, gradient, turning angles, traffic exposure.

60-second demo

Click two points in Zürich Kreis 4. The agent draws three alternative corridors, scores each on a small radar, and checks whether a 2 m lane fits each segment while keeping the remaining road width legal. "Prefer the flattest" re-weights and re-ranks. Export GeoJSON.

Agent tools
  • get_network(bbox) → OSM graph
  • alternatives(a, b, k) → k penalised shortest paths
  • score_corridor(path, weights)
  • check_width(segment, lane_config)
  • compare(paths)
Data
OSM via Overpass or OSMnx. Gradient from swisstopo profiles, already wrapped in your scaffold's geo layer but not re-verified here. Traffic exposure from OSM highway class. Road widths from OSM are sparse.
Rules
Lane width and remaining road width thresholds as a rule pack. No verified Swiss or German cycling design values came out of this research, so they would be labelled as assumptions.
Engine
NetworkX penalised k-shortest paths plus four scoring functions. SNMan is the credible "next engine" for full road-space reallocation.
Wow visual
Three corridors drawing themselves in parallel, a street cross-section before and after, the radar re-shaping as weights change.
Ecosystem hook
Scoring functions as plugins with a weights file, and an SNMan integration path that the CTO will recognise.
One-night plan
1.5 hGraph fetch and simplification2.5 hAlternatives, scoring, width check2.5 hMap UI, radar, cross-section1.5 hAgent loop1.0 hDeploy

About ten hours, with the most unknowns.

Cut first
Gradient, then the cross-section.
Risk
Routing quality on messy OSM graphs, DEM call latency, missing widths. It also invites the closest comparison with goNEON's real product, which cuts both ways.
Scores well because
It is literally one of their listed use cases and builds on the CTO's own research. Pick it if you want the vision video to land hardest and accept more build risk.
Rank 5

One Street

Two rulebooks, one street: the tree agent and the line agent negotiate until nothing conflicts.

60-second demo

A suburban street with a distribution line overhead. The agent places trees, then flags every tree inside the corridor whose mature height exceeds 3 m, swaps in a small species or shifts it, keeps the 15 m radius around masts clear, and narrates each resolution.

Agent tools
The union of Clearance and Canopy plus resolve_conflicts(sites, corridors).
Data and rules
Both verified sets above. The E.DIS 3 m height limit inside the strip is the rule that joins the two domains, and it is above ground on both sides.
Wow visual
Two constraint fields overlapping in different hatches, conflicts resolved one at a time with the reasoning trace, final state with zero red.
Ecosystem hook
Proof that rule packs compose. A third pack from any team slots into the same negotiation.
One-night plan
About twelve hours. Only reachable as a stretch if Clearance or Canopy is working by midnight.
Risk
High. Two live data domains and a resolution loop in one run is where autonomous builds stall with nothing shippable.
Rank 6

Kerbside

Where can the city put EV chargers without blocking sight lines, trees, or loading zones?

60-second demo
Pick a district; parking bays light up by a demand proxy from nearby points of interest; the agent proposes sites and rejects those in conflict with trees, crossings, or loading zones.
Data and rules
OSM parking lanes and existing charging stations, the tree cadastre. The KEA-BW municipal charging guideline was fetched but none of its rules survived verification, so siting rules would be assumptions.
Why last
The demo is a heat map rather than geometry, the rules are unverified, and the ecosystem hook is weaker. Keep it as a hackathon challenge idea for the vision video rather than the MVP.

Architecture shared by all six

Keep the model as orchestrator and explainer, never as the geometry engine. Every tool is deterministic, typed, and returns a short observation the model can reason about. Rule packs are data with attribution, loaded at runtime. Outputs are map layers and GeoJSON, not CAD, matching what goNEON itself delivers.

  • Backend: your FastAPI and Shapely scaffold in LV95, one container. Tool schemas shared between the HTTP API, the agent loop, and an MCP server so the same six tools serve planners, the chat, and third-party agents.
  • Frontend: MapLibre with PMTiles read straight from static hosting. Protomaps documents this through addProtocol; the host needs Range requests and CORS, no tile server.
  • Agent loop: Anthropic or OpenAI tool calling with streamed reasoning shown beside the map. Your scaffold's manual panel, which works without any key, is exactly the "not a solo demo" safeguard the brief rewards.
  • Prior art to crib the UI from: OpenAssistant (GeoDaCenter, MIT, alpha) for the chat-plus-tools pattern over the Vercel AI SDK. Its routing tool is really Mapbox and it has no engineering geometry, so borrow the pattern, not the package.
Not verified by this research: hosting cost and rate limiting for 100 concurrent users, MCP server specifics, and the Zürich endpoints in your scaffold. Sensible defaults: one Fly.io or Railway container, the API key held server-side, a per-session token bucket and a daily cap, and the manual panel as the no-key path.

Do not hardcode these

  • Refuted, 1 to 2 vote: that DIN EN 50341-2-4 defines horizontal distances of 10 m up to 45 kV, 20 m up to 110 kV, 30 m above. The source was one project's compliance note, not the standard, which is paywalled.
  • Refuted, 0 to 3 vote: that Overture ships five themes as GeoParquet filterable by bbox in DuckDB exactly as described. Re-check the current Overture docs before scripting the download.
  • Split vote, 2 to 1: that tool design rather than model reasoning is the ceiling for GIS agents. One paper's self-evaluation; directionally useful, not a law.

Open questions worth ten minutes before you start

  • Does N! expose any API, export format, or rule file that the ecosystem hook should mirror? Nothing public was found either way.
  • Which 380 kV and 220 kV protective strips do Swissgrid or Axpo publish, so the Clearance demo in Zürich uses a Swiss operator's pack rather than a Brandenburg one?
  • Are the Zürich WFS layers in your scaffold answering with CORS today? The Berlin endpoints were probed; the Swiss ones were not.
